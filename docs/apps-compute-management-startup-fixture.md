The script requires both exact clean source checkouts and the preloaded Compute index image; it has no floating-source or floating-image fallback.

The preflight refuses collisions; checks private file modes, exact contexts, localhost bootstrap endpoints, one arm64 node and pinned image preload; checks Ready Milo core and pinned Compute CRDs, Milo serving CA/SAN, three existing Projects and native ResourceClaim discovery, cert-manager CSI driver, and Ready DFW Karmada member. It requires all **16 source-owned hub CRDs to be absent**, so Flux cannot intentionally adopt a pre-existing CRD. Existing Karmada-native CRDs are outside the rendered bundles and remain untouched. It verifies the private runtime IP against the task-owned hub Kind node through the explicit dedicated Docker socket. It verifies Karmada's public serving CA and `localhost` SAN through the host-published loopback endpoint and requires the same NodePort. The pinned Karmada chart's CA lacks a KeyUsage extension, so the Python 3.14 probe disables only `VERIFY_X509_STRICT`; CA-chain and hostname verification remain required. The runtime kubeconfig uses the private bridge IP with the same CA and `tls-server-name: localhost`; host macOS cannot directly probe that bridge IP, so manager startup is the runtime connectivity gate. The preflight does not create any object.

Execution first creates a separate Karmada `default/apps-a1t-hub-crd-installer` ServiceAccount, exact ClusterRole, binding and 55-minute TokenRequest using only the host-held Karmada administrator kubeconfig. The role can create `apiextensions.k8s.io/customresourcedefinitions` because Kubernetes RBAC cannot constrain create by resource name; its get/update/patch/delete verbs are restricted to the exact 16 rendered names. It has no Secret, RBAC, impersonation, workload or native Karmada resource grant. Named positive authorization reviews and **actual forbidden GETs** for a native Karmada CRD and Secret run before mounting this token anywhere. Only its scoped token and public serving CA enter a task-owned host Flux Secret. Two separate host Flux Kustomizations then apply the Compute and NSO source-owned CRD bundles to Karmada. The script checks exact source and applied revisions, `Established=True`, run ownership labels and the 16 live schema hashes before it starts management. Manager Flux depends on both CRD stages. Flux creation is still subject to the narrow interval between the second absence check and remote apply; cleanup refuses to prune a CRD whose observed UID or run label changes.

The optional `--execute` mode creates **exactly three fresh Milo static-token Users** for Project discovery, per-Project controller operations, and quota ResourceClaims. Their reviewed RBAC is installed separately in Milo. It also creates one task-owned Karmada ServiceAccount with a 55-minute TokenRequest and binds only Compute's exact upstream downstream ClusterRole to that ServiceAccount. Hub administrator credentials stay on the host. The fixture creates the reviewed role and one dynamic binding directly through the explicit host-only hub bootstrap config. The unused administrator-credential Flux recipe was removed before submission. The upstream role includes hub Secret mutation, Namespace writes, policies and Compute/NSO resources; these are required controller duties, not a tenant-isolated policy. It grants no Karmada RBAC changes or impersonation.

Before any credential is mounted into the manager, the fixture checks each principal through `kubectl auth can-i` and direct authenticated Milo HTTP requests. Discovery can read real Projects but cannot read Project Secrets; the project controller can read native referenced data and create SubjectAccessReviews but cannot write Secrets or create quota claims; quota can operate ResourceClaims but cannot read Secrets or write Compute objects; the Karmada ServiceAccount can read clusters and create NetworkBindings but cannot change RBAC. The project identity's static RBAC applies across **all** Project control planes, including unrelated Projects. A named missing Secret is probed in provider and consumer Project paths to confirm this known breadth without retrieving Secret values. These checks establish test-overlay RBAC only, not production IAM/OpenFGA or tenant isolation. No allowance or ResourceClaim is fabricated.

Only after the identity probes and hub CRD installation does the script create a task-owned `compute-system` Namespace and four scoped manager kubeconfig Secrets, then reconcile the management Kustomization. Success requires exact Flux source and applied revisions, a Ready management Deployment and Pods with actual image IDs matching the pinned index/arm64 manifest/config chain, both admission webhooks and the watch-sync signals below. The 30-minute startup deadline and separate 10-minute cleanup deadline are bounded. Teardown uses UID/resourceVersion-preconditioned deletes, removes the manager Flux stage **before** the remote CRD stages, revokes the manager binding and CAS-restores Milo's static token CSV, then keeps the CRD installer credential live through remote Flux prune. It verifies all 16 CRDs absent before deleting the scoped Flux Secret and installer role/binding/ServiceAccount. If pruning cannot complete, cleanup reports failure and revokes the installer credential as a security fallback; it does not report a pass. Milo core Flux is CAS-resumed. A non-secret JSON file records results and measured durations. Milo API Pods undergo a rollout to load and unload the temporary token rows; pod identity is not preserved.

The fixture installs NSO **CRDs**, but not an NSO controller. It does not install a Compute cell controller, Locations, entitlement, quota allowance, InstanceType, tenant Workload, Instance, ResourceClaim or route. A successful management startup cannot be reported as an Apps Workload-to-route result. The lead has executed the fixture. Karmada TokenRequest issuance, scoped Flux remote CRD apply/prune, management readiness and the active Instance watch passed in the final lead trial. Earlier failures and their corrections remain recorded below.

## Startup watch signal and timings

A Ready Pod here has stronger meaning than process liveness: the pinned Compute `cmd/main.go` registers `/readyz` checks named `project-discovery-synced` and `projects-engaged`. The first waits for the root Project informer cache to sync; the second requires every currently Ready Project seen in that cache to complete `Engage` with a per-Project cluster. The startup fixture requires the rendered `/readyz` readiness probe and Ready Pod condition. For the separate Karmada hub, Compute's `instance-projector` registers a `source.Kind` on the federation cluster's `Instance` cache. Pinned controller-runtime `v0.24.1` waits for that source's informer and handler sync before logging `Starting workers`. The fixture requires that marker from at least one **current** manager container (the active leader), while every replica must be Ready. A bounded wait allows watch startup after readiness. These checks prove initial Milo and hub watch synchronization without inventing a Workload, quota grant or route; they do not claim ongoing watch health after the observation window or successful reconciliation of tenant resources.

Executed evidence records measured preflight, startup and cleanup durations; a successful run must also record observed Pod image IDs. The separate cleanup deadline is 600 seconds even if the 1800-second startup deadline expires. Final successful watch-sync and cleanup evidence follow the earlier failure records below.

## Native Milo admission stage

Append `--native-admission` to the offline command to validate the additional pinned source, Workload fixture and current CRD schema; this optional check requires Python `jsonschema`. Append the flag with `--execute` to the reviewed isolated run only after a fresh preflight. The normal management fixture remains unchanged when the flag is absent. The lead has now run this optional stage against the private Milo Project API; the result and limits are recorded below.

The optional stage renders the exact two Compute management webhook configurations from the clean pinned source. It requires their six known hook names, rules, paths, `failurePolicy: Fail`, `sideEffects: None`, and `admissionReviewVersions: [v1]`. It preserves `clientConfig.service` pointing to `webhook-service.compute-system.svc`; Milo's pinned default service resolver resolves this DNS name from its API-server Pod rather than requiring a second Service object in Milo storage. The stage adds only the verified **public** CA from the task-owned cert-manager CA Secret to each webhook's `caBundle`; the CA private key stays in the host cluster. It checks the observed Milo configurations against the exact source fields, allowing only known API-server defaults.

The management Flux overlay applies these configurations to the **host** API. Milo's root admission store is distinct, so this bounded test registers the source-rendered copies through Milo's API with a fresh static User, not by copying an administrator kubeconfig into Flux. The User is added and later removed in the same UID- and value-tested static-auth Secret lifecycle as the three management Users. Its ClusterRole permits creating the two admissionregistration kinds (Kubernetes RBAC cannot restrict create by object name), then only named get/delete on `compute-mutating` and `compute-validating`. It has no list/watch/update/patch, Secret, RBAC, impersonation or Workload rights; authorization and an actual Secret GET denial are checked before use. Create uses the scoped direct-TLS kubeconfig, and cleanup uses UID/resourceVersion-preconditioned Milo deletes. The direct registration is an explicit test bootstrap exception: the application webhooks and service remain source-owned and Flux-managed in the host cluster, while the temporary Milo copies have strict collision and ownership guards.

After the manager and host webhook Pods are Ready, the runner verifies the consumer Project UID and that genuine Project Location `dfw` is absent. With Milo's copies absent, it submits the pinned upstream Workload fixture as an authenticated `dryRun=All` request through the **real Project control-plane API**. The fixture is validated offline against the pinned Workload CRD, substitutes a digest-pinned container image, and names a unique probe Workload. The absent-webhook request must return a Workload with HTTP 201; `GET` must still return 404. After both fail-closed Milo configurations are installed, the same dry-run must be rejected by the named `vworkload.kb.io` validator for missing Location `dfw`. DNS, TLS, schema, authentication, generic webhook-call and other errors do not count. The runner compares the full existing Workload item list before and after each dry-run and rechecks the Project UID and probe-name absence. It neither persists a Workload nor supplies a fake Location, entitlement or quota allowance. A validator rejection proves admission delivery and semantic validation, not a positive native Workload or Apps install.

Milo webhook registrations are removed **before** the host manager, CA and CRDs. If either registration's absence cannot be established, cleanup reports failure and retains the manager, CA, runtime Flux, Milo core suspension and hub CRDs for recovery rather than stranding live `failurePolicy: Fail` webhooks. It attempts to revoke the admission installer token and binding while retaining the three manager identities. The separate Karmada CRD installer grant is revoked as an emergency fallback, so manual recovery may need a new scoped installer credential before remote Flux prune. The evidence records revocation outcomes and the retained state. The lead must verify Milo webhook UIDs, remove them safely, then finish teardown. The 30-minute execution and separate 10-minute cleanup bounds still apply, with an additional bounded emergency revocation allowance if recovery is needed.
